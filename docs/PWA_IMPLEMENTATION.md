# ATS Progressive Web App (PWA)

ATS is installable as a Progressive Web App: it can be added to the home
screen / desktop from supported browsers, opens in a standalone window with
ATS branding, shows a branded offline fallback when the network is down, and
notifies users when a new version is deployed. All existing authentication,
authorization, CSRF, sessions, routes and workflows are untouched.

## Manifest

`/manifest.webmanifest` is generated by `PwaManifestController` from
`config/pwa.php`, so name, short name and colours are configurable via env
without editing a static file:

- name: **Assignment Tracking System**, short name: **ATS**
- `start_url` `/`, `scope` `/`, `display: standalone`, `orientation: any`
- `display_override: ["window-controls-overlay", "standalone"]` — desktop
  Chromium offers the Window Controls Overlay; everything else uses the
  plain standalone window
- theme colour `#155dfc` (ATS primary token `--pri`), background `#f7f6f2`
  (page token `--page`)
- Icons: 72–512 px (`purpose: any`) plus 192/512 maskable variants
  (crest at 68% inside the safe zone so circular masks never clip it), all
  generated from `public/images/moes-crest.jpg`.

## Service-worker caching rules

`public/service-worker.js` uses versioned caches
(`ats-v1-static`, `ats-v1-runtime`) and an **allowlist-only** model:

| Request | Strategy |
| --- | --- |
| Non-GET (login, logout, task actions, uploads, approvals…) | **Not intercepted** — network only, fails visibly offline |
| Navigations (all HTML pages) | **Network only, never cached**; branded offline fallback when unreachable |
| `/build/*` (hashed Vite assets), `/pwa/*`, `/images/*`, `/favicon.ico` | **Cache first** (runtime cache, capped at 80 entries) |
| Everything else (Inertia JSON, `/evidence/*`, `/mail-attachments/*`, reports, exports, cross-origin) | **Not intercepted** — network only |

Precached at install: `offline.html`, `pwa/offline.js`, the 192/512 icons,
the crest, and the favicon. Hashed Vite bundles are cached at runtime rather
than precached, so the worker never references stale build filenames.

### Why nothing sensitive can be cached

- No HTML response is ever written to Cache Storage, so no authenticated
  page, dashboard, report or record can be replayed from cache — including
  via the back button after logout.
- Attachment/evidence downloads and previews are served under routes that
  are not on the static allowlist.
- Non-GET requests are never touched, so CSRF tokens, sessions and redirects
  behave exactly as before.

## Registration and environments

`resources/js/pwa/register-service-worker.ts` registers the worker only when
**all** are true: browser support + secure context (HTTPS or localhost), the
`<meta name="ats-pwa" content="enabled">` tag is present (i.e.
`PWA_ENABLED=true`), and the bundle is a production build. During
`npm run dev`, or when the PWA is disabled, any previously installed worker
is actively **unregistered** so caching never interferes with HMR or
debugging.

## Desktop title bar (Window Controls Overlay)

On desktop Chromium (Chrome/Edge on Windows, macOS, Linux) the installed
app can extend its content into the title-bar strip. The manifest opts in
via `display_override`, and `resources/js/pwa/title-bar.tsx` renders a
custom title bar **only while** `navigator.windowControlsOverlay.visible`
is true:

- The bar is positioned and sized purely by the CSS
  `env(titlebar-area-x/y/width/height)` variables, so it occupies exactly
  the strip the OS leaves free. The **native Windows minimize / maximize /
  close buttons stay native** — they are never covered, recreated, or
  replaced (macOS traffic lights on the left are equally respected, since
  `titlebar-area-x` shifts the bar right in that case).
- The whole strip is a drag region (`app-region: drag`); every interactive
  element inside it (`a`, `button`, `input`) is explicitly `no-drag`.
- Content: crest icon + application name (draggable area), an amber
  "Offline" chip while disconnected (`role="status"`), and a
  keyboard-accessible dashboard shortcut for signed-in users (white
  focus-visible outline on the brand-blue bar; contrast passes WCAG AA).
- The bar background is the brand primary `#155dfc` — the same colour as
  the manifest `theme_color` Chromium paints behind the system controls,
  so bar and controls strip read as one seamless native title bar.
- While the overlay is active, `html.wco-active` reserves
  `env(titlebar-area-height)` of top padding on the application frame and
  shifts the offline banner down, so no layout is ever hidden underneath.

Geometry changes are tracked live through the `geometrychange` event:
toggling the overlay from the chevron menu, resizing the window, or
entering fullscreen (where the overlay disappears) all add/remove the bar
and its reserved space at runtime.

**Fallbacks:** in a browser tab, in fullscreen, on mobile, in Safari or
Firefox, or in a standalone window where the user turned the overlay off,
the component renders nothing and the standard title bar — painted with the
manifest theme colour and showing the document title — is used. No feature
detection is exposed to the rest of the app; nothing else changes.

**Testing the overlay:** install ATS from Chrome/Edge on Windows, then
click the chevron (⌄) next to the window controls (or the three-dot menu →
"Show window controls overlay") to toggle it. Verify: dragging the strip
moves the window; the crest, name and (when offline) the amber chip render
on the blue strip; the dashboard shortcut is clickable and Tab-reachable;
native minimize/maximize/close still work; disabling the overlay restores
the standard title bar with no blank gap at the top of the page.

## Installation

- **Chromium (Chrome/Edge, desktop and Android):** the browser fires
  `beforeinstallprompt`; ATS shows a dismissible "Install ATS" card
  (bottom-left). "Not Now" or dismissing hides it for 14 days
  (`localStorage` key `ats-pwa-install-dismissed-at`). It never shows while
  already running standalone, and stops after installation.
- **iOS/iPadOS Safari:** no prompt API exists; a one-time guidance card
  explains Share → "Add to Home Screen". Same 14-day dismissal.
- **Firefox desktop:** does not support installation; everything else
  (offline fallback, status, updates) still works.

## Offline behaviour

- A persistent amber banner ("You are offline…") appears while offline and
  a "Connection restored" toast appears on recovery (both `role="status"`,
  `aria-live="polite"`).
- Navigating while the server is unreachable shows `public/offline.html`
  (ATS-branded, mobile responsive, Try Again + Return to Dashboard).
- Submitting any form while offline is cancelled **before** anything is
  sent, with the toast "This action requires an internet connection. Your
  changes have not yet been submitted." Form state is preserved, nothing is
  marked as saved until the server confirms it, and no duplicate submission
  can occur on reconnect.

## Version updates

1. Deploy (see below). Returning clients download the changed
   `service-worker.js`; the new worker installs and **waits** — it never
   activates while the old one controls open pages.
2. ATS shows "A new version of ATS is available" with **Refresh Now** /
   **Later**. Refresh Now messages the waiting worker (`SKIP_WAITING`) and
   reloads exactly once on `controllerchange` (guarded against loops).
   "Later" defers; the update activates when all ATS tabs close.
3. On activation, all caches from older `CACHE_VERSION`s are deleted.

**Cache-version update procedure:** when you change the service worker's
caching logic or precache list, bump `CACHE_VERSION` in
`public/service-worker.js` (`ats-v1` → `ats-v2`). Routine app deploys do
not require a bump — hashed asset URLs change by themselves and navigations
are never cached.

## Changing icons and colours

- **Colours:** set `PWA_THEME_COLOR` / `PWA_BACKGROUND_COLOR` in `.env`
  (defaults mirror the design tokens in `resources/css/app.css`). Run
  `php artisan config:clear` after changing.
- **Icons:** replace `public/images/moes-crest.jpg`, then regenerate every
  size in `public/pwa/icons/` (same filenames; sizes listed in
  `config/pwa.php`). Standard icons are the source scaled to 94% on a white
  square; maskable icons use 68% so the crest stays inside the ~80% safe
  zone. Any image tool works as long as sizes and names match.

## Disabling the PWA

Set `PWA_ENABLED=false` and `php artisan config:clear`. The layout stops
emitting the manifest and PWA meta tags, and the frontend unregisters any
existing service worker on the next visit. The application functions
normally as a plain web app.

## Production deployment requirements

1. **HTTPS is required** (service workers only run in secure contexts;
   localhost is exempt for development). Ensure HTTP redirects to HTTPS and
   the certificate is valid; the app already sends HSTS on secure requests
   (`SecurityHeaders` middleware). Registration is automatically skipped on
   insecure origins — no insecure workaround exists or should be added.
2. `npm run build` (hashed assets in `public/build/`), then
   `php artisan config:cache` / `route:cache` as usual.
3. Verify publicly reachable: `/manifest.webmanifest` (200,
   `application/manifest+json`), `/service-worker.js` (200, served from the
   origin root so its scope is `/`), `/offline.html`, `/pwa/icons/*.png`.
4. The existing production CSP (`SecurityHeaders`) already covers the PWA:
   same-origin scripts/styles/images only; no inline scripts are used
   (offline page logic lives in `/pwa/offline.js`). No header was weakened.

## Testing

Automated: `php artisan test --filter=PwaTest` (manifest identity and
availability, icon files, worker/offline assets, conditional tags).

Manual checklist (Chrome/Edge DevTools → Application):

- **Install:** install from the address-bar icon or the in-app card; the
  installed app opens standalone, named "Assignment Tracking System"
  ("ATS" short) with the crest icon; start URL `/` redirects through auth
  correctly.
- **Offline:** DevTools → Network → Offline → navigate: branded offline
  page appears; Cache Storage contains only `/build/`, `/pwa/`, `/images/`
  and favicon entries — never HTML, never attachments; submitting a form
  offline shows the not-submitted toast and keeps the form.
- **Update:** deploy a change (or edit `service-worker.js`), reload once —
  the update prompt appears; Refresh Now reloads once with no loop; old
  caches disappear after a `CACHE_VERSION` bump.
- **Security:** log out, press Back — no protected page is served from
  cache; `/login` responds normally; Lighthouse → PWA/Best Practices for a
  final audit.

Browsers: Chrome (Android/Windows), Edge (Windows), Safari (macOS/iOS —
install via Add to Home Screen only), Firefox (no install support; core
behaviour unaffected).

## Known browser limitations

- iOS Safari has no `beforeinstallprompt`; users install via the Share
  menu. iOS may evict service workers / caches for rarely-used sites; the
  app degrades gracefully to a normal web app.
- Firefox desktop cannot install PWAs.
- `background_color`/splash screens are Android-only; desktop ignores them.

## Push notifications (future)

Not implemented — deliberately. The service worker and registration module
are the natural attachment points for a future `push` + `notificationclick`
handler once a notification service exists server-side. Permission must only
be requested after an explicit user action, never on login/page load.
